1. 웹의 기본 구조: 브라우저와 서버

웹 서비스를 사용할 때 브라우저는 클라이언트(Client)이고, 요청을 받아 처리하는 프로그램은 서버(Server)다.

클라이언트가 HTTP 요청(Request)을 보내면 서버는 처리 결과를 HTTP 응답(Response)으로 돌려준다.

브라우저는 응답으로 받은 HTML, CSS, JavaScript 및 기타 리소스를 해석해 페이지를 표시한다.

예를 들어 주소창에 https://example.com/login을 입력하면 일반적으로 DNS를 통해 서버 주소를 확인하고, 서버와 연결을 수립한 뒤, HTTPS에서는 TLS로 통신을 보호한다.

이후 브라우저가 페이지를 요청하고 서버가 응답한다.

실제 세부 연결 절차는 HTTP/1.1, HTTP/2, HTTP/3 및 연결 재사용 여부에 따라 달라질 수 있다.

2. HTTP Request와 Response

2-1. HTTP Request

아래는 HTTP/1.1의 텍스트 표현이다. 시작 줄, 헤더, 빈 줄, 선택적인 본문으로 구성된다.

GET /login HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0
Accept: text/html
  • GET: 요청 메서드. 주로 리소스 조회에 사용한다.
  • /login: 요청 경로.
  • HTTP/1.1: HTTP 버전.
  • Host: 요청 대상 호스트.
  • User-Agent: 클라이언트 프로그램 정보.
  • Accept: 클라이언트가 처리 가능한 응답 미디어 타입.

위 요청은 본문이 없다. 모든 요청에 Body가 존재하는 것은 아니다. 또한 HTTP/2와 HTTP/3는 HTTP/1.1의 시작 줄을 그대로 전송하지 않고, 의사 헤더(:method, :path 등)를 사용하는 다른 메시지 표현을 갖는다. Burp Suite는 분석하기 편한 텍스트 형태로 보여줄 수 있다.

2-2. HTTP Response

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 19

응답은

상태 줄, 응답 헤더, 빈 줄, 선택적인 본문으로 구성된다.

위 예시 본문은 ASCII 기준 19바이트다. HTTP 상태 코드의 첫 번째 숫자를 보면 대략적인 분류를 이해할 수 있다.

200 OK 성공적으로 처리됨
301 / 302 리다이렉트 Location 헤더 확인
400 Bad Request 파라미터 누락·형식 오류 등
401 Unauthorized 인증 관련 응답
403 Forbidden 권한 거부 여부 조사
404 Not Found 경로 및 리소스 확인
500 Internal Server Error 서버 내부 오류

물론, 상태 코드만으로 비즈니스 로직의 성공·실패를 완전히 확정할 수는 없다. 응답 Body, 재접속 결과, 계정 권한 변경 여부 등도 확인해야 한다.

3. Header와 Body의 차이

Header는 요청 또는 응답을 해석하는 데 필요한 메타데이터이며, Body는 실제로 전송하는 본문이다. 아래 로그인 요청에서 빈 줄 위는 헤더이고 빈 줄 아래가 본문이다.

POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=kim&password=1234

Content-Type: application/x-www-form-urlencoded는 본문이 웹 폼 인코딩 방식이라는 뜻이다.  username=kim&password=1234는 본문 데이터다.

 

4. GET과 POST, Query String

4-1. GET

GET은 주로 리소스를 조회한다. URL에서 ?는 경로와 Query String을 구분하고, &는 여러 파라미터를 구분한다.

GET /search?keyword=apple&page=2 HTTP/1.1
Host: example.com

이 예시의 Path는 /search이고, Query Parameter는 keyword=apple과 page=2다.

4-2. POST

POST는 데이터를 제출해 서버에 처리를 요청할 때 많이 사용한다. 웹 폼에서는 Body에 데이터를 담는 것이 일반적이다.

POST /login HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

username=kim&password=1234

GET과 POST의 차이는 'GET에는 무조건 Body가 없고 POST에는 무조건 Body가 있다'는 뜻이 아니다.

GET 본문은 일반적으로 정의된 의미가 없고 상호운용성 문제가 있어 권장하지 않는다.

POST 요청도 URL의 Query String을 함께 사용할 수 있다.

중요한 것은 요청 메서드, 데이터의 실제 위치, 서버가 값을 읽는 방식을 함께 이해하는 것이다.

5. Cookie와 Session, 인증과 인가

HTTP는 기본적으로 각 요청을 독립적으로 처리한다. 로그인 상태를 유지하기 위해 웹 애플리케이션은 흔히 세션 식별자를 쿠키에 담아 사용한다. 서버가 다음과 같이 쿠키를 설정할 수 있다.

HTTP/1.1 200 OK
Set-Cookie: session=EXAMPLE_SESSION; HttpOnly; Secure; SameSite=Lax

브라우저는 이후 해당 사이트에 대한 요청에 쿠키를 포함할 수 있다.

GET /my-account HTTP/1.1
Host: example.com
Cookie: session=EXAMPLE_SESSION

쿠키는 브라우저에 저장되는 이름·값 등의 데이터이고, 서버 세션은 서버 측 로그인 상태를 관리하는 방식 중 하나다. 실제 세션 저장 방식은 구현마다 다르므로 모든 웹사이트가 서버 측 세션 저장소를 사용하는 것은 아니다.

인증(Authentication)은 '누구인가?'를 확인하는 과정이고, 인가(Authorization)는 '이 사용자가 이 기능을 실행할 권한이 있는가?'를 판단하는 과정이다. 로그인되어 있어도 관리자 기능의 사용 권한은 없을 수 있다. 

6. HTTP 관찰 및 로컬 실습

6-1. Chrome 개발자 도구

  1. Chrome에서 웹사이트를 연다.
  2. F12로 개발자 도구를 열고 Network 탭을 선택한다.
  3. 페이지를 새로고침하고 문서 요청을 선택한다.
  4. Headers에서 Request URL, Request Method, Status Code, Request/Response Headers를 확인한다.
  5. Response 탭에서 HTML 또는 JSON 응답 본문을 확인한다.

실제 헤더는 브라우저 버전, 서버, 연결 방식에 따라 달라진다. 모든 HTTP 요청이 개발자 도구에 동일한 모양으로 표시되는 것은 아니다.

 

6. 실전문제풀이

접근 제어는 특정 사용자에게 어떤 리소스와 기능을 허용할지 결정하는 보안 통제다. 일반 사용자가 관리자 기능을 실행할 수 있게 되면 수직적 권한 상승(Vertical Privilege Escalation)이 발생할 수 있다.

관리자 링크를 화면에서 숨기거나, 관리자 URL을 복잡하게 만들거나, 특정 HTTP Method에서만 검사하는 것은 적절한 인가를 대체하지 못한다. 서버는 실제 실행되는 모든 보호 기능에 대해 요청자의 권한을 확인해야 한다.

 

분석 방법: (1) 문제 설명에서 가설 수립 → (2) URL·HTML·JS·공개 파일·요청 정보 수집 → (3) 정상 동작 요청 확보 → (4) 세션·메서드·파라미터를 한 번에 하나씩 변경 → (5) 응답과 실제 서버 상태를 비교한다.

7. Write-up 01: Unprotected admin functionality

Unprotected admin functionality (Apprentice)

7-1. 목표와 분석

접근 제어가 없는 관리자 패널을 찾아 carlos 사용자를 삭제한다. 관리자 링크가 보이지 않더라도 관리자 기능 자체가 없다는 것은 아니었다.

7-2. 정보 수집: robots.txt

사이트 루트에 /robots.txt를 붙여 요청한다.

GET /robots.txt HTTP/1.1
Host: LAB_HOST

공식 실습의 단서는 다음과 같은 내용이다.

User-agent: *
Disallow: /administrator-panel

User-agent: *는 모든 크롤러에 적용되는 규칙을 나타내고, Disallow는 지정 경로를 크롤링하지 말라는 요청이다. 

7-3. 취약점 검증 및 풀이

공개된 관리자 경로로 이동한다.

GET /administrator-panel HTTP/1.1
Host: LAB_HOST

관리자 권한을 증명하지 않고 관리자 화면에 진입할 수 있다. 관리자 패널에서 carlos 사용자를 삭제하여 문제를 완료한다.

7-4. 근본 원인과 대응

취약점의 본질은 robots.txt 자체가 아니라 관리 기능에 서버 측 인가 검사가 없다는 것이다.

모든 관리자 페이지와 API에 실제 사용자 권한 검사를 적용하고, 원칙적으로 허용되지 않은 접근을 거부해야 한다.

8. Write-up 02: Unprotected admin functionality with unpredictable URL

Unprotected admin functionality with unpredictable URL (Apprentice)

8-1. 목표와 분석

추측하기 어려운 관리자 URL을 발견하고 패널에서 carlos를 삭제한다. 경로를 알기 어렵도록 만들었지만 애플리케이션 내부에서 경로가 노출되어 있다.

8-2. HTML과 JavaScript 검사

  1. 실습 웹사이트 메인 화면을 연다.
  2. Ctrl+U로 HTML 소스를 보거나 F12 개발자 도구의 Sources/Elements를 확인한다.
  3. 페이지에 포함된 JavaScript를 찾아 관리자 링크를 생성하는 코드나 URL 문자열을 살펴본다.

아래와 비슷한 코드가 들어있었다.

var isAdmin = false;
if (isAdmin) {
    var link = document.createElement('a');
    link.href = '/admin-EXAMPLE-PATH';
    link.textContent = 'Admin panel';
    document.body.appendChild(link);
}

isAdmin이 거짓이면 링크가 화면에 나타나지 않더라도, JavaScript 소스에 적힌 문자열은 사용자가 확인할 수 있다.

8-3. 경로 접근 및 해결

실제 JavaScript에서 발견한 관리자 URL로 직접 이동하고, 패널에서 carlos를 삭제한다. 

8-4. 근본 원인과 대응

URL을 추측하기 어렵게 만들거나 클라이언트 JavaScript 조건문으로 메뉴를 숨기는 것은 접근 제어가 아니다. 관리자 기능을 제공하는 서버 라우트에서 사용자 인증과 관리자 인가를 별도로 검증해야 한다. 민감한 비밀 값도 클라이언트 JavaScript에 포함하지 않아야 한다.

9. Write-up 03: Method-based access control can be circumvented

Method-based access control can be circumvented (Apprentice)

9-1. 목표 및 계정

HTTP Method에 따라 접근 제어가 불일치하는 기능을 찾아 일반 사용자 wiener의 권한을 관리자로 올려야한다.

  • 관리자 계정: administrator / admin
  • 일반 사용자 계정: wiener / peter

9-2. 정상 관리자 요청 확보

관리자로 로그인하여 관리자 패널의 권한 변경 기능을 실행한 다음, 해당 요청을 Burp Suite Proxy에서 찾아 Repeater로 전송한다. 

POST /admin-roles HTTP/2
Host: LAB_HOST
Cookie: session=ADMIN_SESSION
Content-Type: application/x-www-form-urlencoded

username=carlos&action=upgrade

 

확인해야할  항목은 메서드 POST, 경로 /admin-roles, 세션 쿠키, 권한 변경 대상 username, 변경 동작 action이다.

9-3. 일반 사용자 세션으로 접근 제어 확인

시크릿 창에서 wiener로 로그인한 뒤 Repeater의 쿠키를 일반 사용자 세션으로 바꿔 동일한 POST 요청을 시도한다.

하지만 서버는 Unauthorized라고 응답한다. 

일반 사용자에게 POST 방식의 관리자 기능이 거부됨을 확인할 수 있다.

9-4. HTTP Method 변경 시험

이후 GET 방식으로 변경한다. Burp Suite Repeater의 Change request method 기능을 활용하면 요청을 수정하기 편하다.

9-5. 실패했던 실제 시도와 400 응답

학습 과정에서는 GET으로 바꾸었지만 파라미터를 계속 Body에 둔 요청을 시도했다. 

GET /admin-roles HTTP/2
Host: LAB_HOST
Cookie: session=REDACTED
Content-Type: application/x-www-form-urlencoded

username=wiener&action=upgrade

실제로 관찰한 응답은 다음과 같았다.

HTTP/2 400 Bad Request
Content-Type: application/json; charset=utf-8

"Missing parameter 'username'"

이는 서버가 해당 요청에서 username 파라미터를 찾지 못했다는 뜻이다.

GET Body가 기술적으로 항상 금지된 것은 아니지만, 이 실습의 GET 처리 경로에서는 본문의 폼 데이터를 필요한 쿼리 파라미터로 해석하지 않은 것으로 볼 수 있다.

따라서 메서드만 바꾸는 것이 아니라 파라미터의 위치도 바꿔야 한다.

9-6. 최종 요청과 해결

폼 데이터를 URL의 Query String으로 이동한 뒤 일반 사용자 세션으로 요청한다.

GET /admin-roles?username=wiener&action=upgrade HTTP/2
Host: LAB_HOST
Cookie: session=WIENER_SESSION

GET에서 ?는 경로와 Query String을 구분하고, &는 두 파라미터를 구분한다.

이 요청이 관리 기능을 호출하고 wiener를 관리자로 승격해 실습 목표를 만족한다.

9-7. JavaScript fetch로 시도한 요청이 잘못된 이유

학습 도중 다음 형태의 JavaScript 호출도 시도했다.

fetch('/admin-roles', {
    method: 'GET',
    headers: {
        'username': 'wiener',
        'action': 'upgrade'
    }
});

이 코드는 username과 action을 HTTP 요청 헤더로 전송한다. 하지만 서버가 URL의 Query Parameter를 기대한다면 같은 이름의 커스텀 헤더는 대신 사용할 수 없다.

Header, Query String, Body는 서로 다른 위치임을 이해할 수 있었다.

9-8. 근본 원인과 대응

핵심 문제는 HTTP Method에 따라 관리자 권한 검사가 일관되게 시행되지 않는 것이다. 동일한 관리 작업이 GET 요청에서도 실행된다면 POST에만 권한 검사를 구현한 것은 충분하지 않다. 보호된 기능의 모든 실행 경로에 공통 인가 정책을 적용하고, 서버 상태를 바꾸는 작업을 GET으로 허용하지 않으며, 허용되지 않은 메서드를 명확히 거부해야 한다.
