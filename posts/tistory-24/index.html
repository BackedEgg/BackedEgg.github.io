원래는 netfilter을 활용해 패킷변조를 하려고 했으나 통신과 각계층의 헤더들에 대한 이해가 선행되어야겠다고 판단했다.

 

1. 네트워크 통신에 대하여:

네트워크 통신은 단순히 한 컴퓨터에서 다른 컴퓨터로 데이터를 전달하는 과정이라고 볼 수 없다.

데이터가 목적지에 도달하기 위해서는 여러 프로토콜이 이용된다. 각 프로토콜은 자신이 담당하는 역할에 따라 데이터에 헤더(Header)를 추가하며, 수신 측은 해당 헤더를 분석해 데이터를 처리한다.

예를 들어 웹 브라우저에서 웹사이트에 접속하면 다음과 같은 과정이 진행될 수 있다.

  1. DNS를 이용해 도메인 이름에 해당하는 IP 주소를 확인한다.
  2. 라우팅 테이블을 확인해 데이터를 전달할 경로를 결정한다.
  3. 필요한 경우 ARP를 이용해 다음 홉의 MAC 주소를 확인한다.
  4. Ethernet 프레임을 생성해 네트워크로 전송한다.
  5. 라우터들이 IP 헤더를 확인해 패킷을 목적지 방향으로 전달한다.
  6. TCP를 사용하는 경우 연결을 설정한다.
  7. HTTPS에서는 TLS를 통해 암호화 통신을 준비한다.
  8. 애플리케이션 데이터를 주고받는다.
  9. 통신이 끝나면 연결을 종료하거나 재사용한다.

이 글에서는 이러한 통신 과정을 이해하기 위해 다음 프로토콜을 분석한다.

Ethernet 같은 링크에서 프레임 전달
ARP IPv4 주소에 대응하는 MAC 주소 확인
IPv4 32비트 IP 주소 기반의 패킷 전달 및 라우팅
IPv6 128비트 주소 기반의 패킷 전달 및 라우팅
TCP 신뢰성 있는 바이트 스트림 제공
UDP 비연결형 데이터그램 전달
ICMP 네트워크 오류 전달 및 상태 진단

2. 네트워크 통신의 기본 구조

2.1 OSI 7계층과 TCP/IP 모델

네트워크 통신을 이해하려면 먼저 프로토콜이 계층별로 구분된다는 사실을 알아야 한다.

OSI 7계층은 네트워크 기능을 일곱 단계로 나눈 개념적 참조 모델이다.

7 Application 애플리케이션 서비스 제공 HTTP, DNS
6 Presentation 데이터 표현, 인코딩, 암호화 등 TLS 관련 기능
5 Session 통신 세션 관리 세션 관리 기능
4 Transport 프로세스 간 데이터 전달 TCP, UDP
3 Network 논리 주소 및 라우팅 IPv4, IPv6, ICMP
2 Data Link 링크 내 프레임 전달 Ethernet, Wi-Fi
1 Physical 물리적 신호 전송 케이블, 광신호, 전파

 

실제 인터넷에서는 TCP/IP 프로토콜 모델을 중심으로 통신한다.

OSI 계층은 기능을 설명하기 위한 모델이며, 실제 프로토콜이 항상 한 계층에만 완벽하게 대응하는 것은 아니다.

2.2 캡슐화(Encapsulation)

캡슐화란 상위 계층에서 전달받은 데이터에 하위 계층의 헤더를 추가하는 과정이다.

예를 들어 애플리케이션이 Hello라는 데이터를 TCP로 전송한다고 가정하자.

데이터는 다음과 같이 구성된다.

[Application Data]
       Hello

        ↓ TCP 헤더 추가

[TCP Header][Hello]

        ↓ IP 헤더 추가

[IP Header][TCP Header][Hello]

        ↓ Ethernet 헤더 추가

[Ethernet Header][IP Header][TCP Header][Hello]

각 프로토콜이 자신의 역할에 필요한 정보를 헤더에 추가한다.

Ethernet Header

  • 출발지 MAC 주소
  • 목적지 MAC 주소
  • 상위 프로토콜 식별 정보

IP Header

  • 출발지 IP 주소
  • 목적지 IP 주소
  • 패킷 전달에 필요한 제어 정보

TCP Header

  • 출발지 포트
  • 목적지 포트
  • Sequence Number
  • Acknowledgment Number
  • TCP Flags

Application Data

  • 실제 애플리케이션이 주고받는 데이터

Ethernet을 사용하는 네트워크에서는 이렇게 구성된 데이터가 Ethernet 프레임 형태로 전달된다.

실제 Ethernet 프레임에는 필요한 경우 Padding과 오류 검출을 위한 FCS도 포함된다.

2.3 역캡슐화(Decapsulation)

역캡슐화는 수신 측이 헤더를 순서대로 해석하면서 상위 계층에 데이터를 전달하는 과정이다.

일반적인 Ethernet/IPv4/TCP 통신에서는 다음과 같은 논리적 순서로 진행된다.

Ethernet Frame 수신
        ↓
Ethernet Header 확인
        ↓
IPv4 Header 확인
        ↓
TCP Header 확인
        ↓
Application Data 전달

각 계층은 헤더에 기록된 정보를 이용해 다음 처리 단계를 결정한다.

예를 들어 Ethernet의 EtherType이 0x0800이면 IPv4 패킷으로 해석할 수 있다.

IPv4의 Protocol 값이 6이면 상위 프로토콜이 TCP임을 알 수 있다.

TCP의 Destination Port가 443이면 해당 포트에 연결된 소켓을 찾는 데 사용된다.

단, 443번 포트라는 이유만으로 반드시 HTTPS 서비스가 동작한다고 단정할 수는 없다.

2.4 Frame, Packet, Segment, Datagram

네트워크에서 전달되는 데이터를 계층에 따라 서로 다른 용어로 부른다.

용어계층 또는 프로토콜의미

Frame 데이터링크 계층 링크를 통해 전달되는 데이터 단위
Packet 네트워크 계층 IP 헤더를 포함하는 데이터 단위
Segment TCP TCP 헤더를 포함하는 데이터 단위
Datagram UDP, IP 등 독립적인 데이터 전달 단위

일상적으로 이 모두를 패킷이라고 부르기도 한다.

3. Ethernet Header

3.1 Ethernet이란?

Ethernet은 주로 유선 LAN에서 사용되는 데이터링크 기술이다.

Ethernet의 핵심 역할은 동일한 링크에서 프레임을 어느 장비로 전달할지 식별하고 전달하는 것이다.

이를 위해 MAC 주소를 사용한다.

MAC 주소는 Ethernet 인터페이스를 식별하는 링크 계층 주소이며, 일반적인 Ethernet MAC 주소의 크기는 48비트(6바이트)이다.

 

02:00:00:00:00:10

MAC 주소를 이해할 때 중요한 것은 IP 주소와의 차이이다.

  • MAC 주소: 현재 링크에서 프레임 전달에 사용
  • IP 주소: 네트워크를 가로질러 목적지를 식별하고 경로를 결정하는 데 사용

3.2 Ethernet II 헤더 구조

일반적인 Ethernet II 헤더는 14바이트이다.

+------------------------+
| Destination MAC (6B)   |
+------------------------+
| Source MAC      (6B)   |
+------------------------+
| EtherType       (2B)   |
+------------------------+
| Payload                |
+------------------------+
| FCS             (4B)   |
+------------------------+

FCS는 헤더가 아닌 프레임의 마지막 부분에 위치한다.

필드별 설명

필드크기역할

Destination MAC 6B 프레임을 전달할 대상 MAC 주소
Source MAC 6B 프레임 송신 인터페이스의 MAC 주소
EtherType 2B 페이로드에 포함된 프로토콜 식별

Destination MAC

현재 Ethernet 링크에서 프레임을 전달할 대상이다.

같은 LAN의 다른 컴퓨터로 전송한다면 해당 컴퓨터의 MAC 주소가 사용될 수 있다.

다른 네트워크로 전달한다면 일반적으로 다음 홉인 게이트웨이의 MAC 주소가 사용된다.

Source MAC

해당 Ethernet 프레임을 전송하는 인터페이스의 MAC 주소이다.

EtherType

Ethernet 헤더 뒤에 어떤 프로토콜 데이터가 들어 있는지 나타낸다.

EtherType의미

0x0800 IPv4
0x0806 ARP
0x86DD IPv6
0x8100 IEEE 802.1Q VLAN 태그

예를 들어 EtherType 값이 0x0800이면 Ethernet 페이로드를 IPv4 패킷으로 처리할 수 있다.

3.3 Ethernet 프레임의 크기

일반적인 Ethernet II 프레임은 VLAN 태그가 없을 때 다음과 같은 크기 규칙을 가진다.

구성크기

Ethernet Header 14B
Payload 일반적으로 46~1500B
FCS 4B
전체 프레임 일반적으로 64~1518B

위 크기는 표준적인 기본 Ethernet 프레임을 기준으로 한 값이다. VLAN 태그나 Jumbo Frame 등을 사용하면 달라진다.

Payload가 너무 짧으면 최소 프레임 크기를 만족시키기 위해 Padding을 추가할 수 있다.

FCS(Frame Check Sequence)는 전송 과정에서 발생한 비트 오류를 검출하는 데 사용된다.

 

3.4 라우터를 통과하면 MAC 주소는 어떻게 될까?

다음 통신을 가정하자.

PC A
IP: 192.168.1.10
    |
    v
Gateway
IP: 192.168.1.1
    |
    v
Internet
    |
    v
Server
IP: 203.0.113.20

PC A가 서버에 데이터를 보낼 때 첫 번째 Ethernet 프레임의 목적지 MAC은 일반적으로 게이트웨이의 MAC이다.

라우터는 해당 프레임을 수신한 뒤 IP 패킷을 확인하고 다음 경로를 결정한다.

이후 다음 링크에 맞는 새로운 데이터링크 헤더를 구성한다.

즉, 일반적인 Ethernet 기반 라우팅에서는 다음과 같은 현상이 발생한다.

구분PC → GatewayGateway → 다음 홉

Source MAC PC MAC Gateway 출력 인터페이스 MAC
Destination MAC Gateway MAC 다음 홉 MAC
Source IP PC IP PC IP
Destination IP Server IP Server IP

이 예시는 NAT가 적용되지 않는 경우이다.

핵심: MAC 주소는 링크마다 변경될 수 있지만, IP 주소는 일반적인 라우팅 과정에서 유지된다.

다만 NAT가 수행되면 IP 주소도 변경될 수 있다.

4. ARP Header

4.1 ARP란?

ARP(Address Resolution Protocol)는 IPv4 주소에 대응하는 링크 계층 주소를 알아내기 위한 프로토콜이다.

일반적인 Ethernet 환경에서는 IPv4 주소에 대응하는 MAC 주소를 확인할 때 사용한다.

예를 들어 다음과 같은 상황을 생각해 보자.

PC IP       : 192.168.1.10
Gateway IP  : 192.168.1.1
Gateway MAC : 알 수 없음

PC는 게이트웨이의 IP 주소를 알고 있지만 MAC 주소를 모른다.

Ethernet 프레임을 만들려면 목적지 MAC 주소가 필요하므로 이를 알아내야 한다.

이때 ARP를 사용할 수 있다.

4.2 ARP 동작 과정

① ARP Request

PC는 같은 네트워크에 ARP Request를 전송한다.

의미는 다음과 같다.

192.168.1.1이라는 IP 주소를 사용하는 장비는 자신의 MAC 주소를 알려주세요.

일반적인 ARP Request는 Ethernet 브로드캐스트 주소를 사용한다.

ff:ff:ff:ff:ff:ff

따라서 같은 브로드캐스트 도메인의 장비들이 요청을 수신할 수 있다.

② ARP Reply

해당 IP를 사용하는 장비가 ARP Reply를 전송한다.

예:

192.168.1.1의 MAC 주소는
02:00:00:00:00:01입니다.

일반적인 ARP Reply는 요청한 장비를 대상으로 유니캐스트 전송된다.

③ ARP 캐시 저장

PC는 알아낸 IP-MAC 주소 대응 관계를 이웃 캐시에 저장한다.

192.168.1.1
    ↕
02:00:00:00:00:01

이후 일정 시간 동안 같은 주소를 사용할 경우 저장된 정보를 활용할 수 있다.

ARP 캐시가 존재한다고 해서 매번 ARP 요청이 발생하는 것은 아니다.

4.3 ARP 헤더 구조

Ethernet과 IPv4에서 사용하는 일반적인 ARP 메시지의 크기는 28바이트이다.

필드크기역할

Hardware Type 2B 하드웨어 주소 유형
Protocol Type 2B 프로토콜 주소 유형
Hardware Size 1B 하드웨어 주소 길이
Protocol Size 1B 프로토콜 주소 길이
Opcode 2B 요청 또는 응답 종류
Sender MAC 6B 송신자 MAC
Sender IP 4B 송신자 IPv4
Target MAC 6B 대상 MAC
Target IP 4B 대상 IPv4

 

필드값의 의미

Hardware Type 1 Ethernet
Protocol Type 0x0800 IPv4
Opcode 1 ARP Request
Opcode 2 ARP Reply

일반적인 ARP Request는 대상 MAC을 아직 모르기 때문에 Target Hardware Address를 0으로 채울 수 있다.

여기서 주의할 점은 Ethernet 헤더의 Destination MAC과 ARP 메시지 내부의 Target MAC이 서로 다른 필드라는 것이다.

4.4 ARP와 보안

ARP는 기본적으로 강력한 송신자 인증 기능을 제공하지 않는다.

따라서 공격자가 허위 ARP 응답을 보내 잘못된 IP-MAC 대응 관계를 만들면 트래픽이 의도하지 않은 장비로 전달될 수 있다.

이러한 공격을 ARP Spoofing 또는 ARP Poisoning이라고 부른다.

ARP Spoofing은 중간자 공격(Man-in-the-Middle)의 한 수단으로 악용될 수 있다.

참고: IPv6에서는 일반적으로 ARP 대신 ICMPv6 기반 Neighbor Discovery Protocol(NDP)을 사용한다.

5. IPv4 Header

5.1 IPv4란?

IPv4(Internet Protocol version 4)는 IP 주소를 기반으로 패킷을 네트워크 간에 전달하는 프로토콜이다.

IPv4 주소의 크기는 32비트이다.

192.168.1.10

IPv4는 연결 설정 없이 패킷을 독립적으로 전달하는 비연결형 프로토콜이다.

또한 Best-Effort 방식으로 동작한다.

즉, IP 자체는 다음을 보장하지 않는다.

  • 패킷이 반드시 목적지에 도착하는 것
  • 패킷이 순서대로 도착하는 것
  • 패킷이 중복되지 않는 것
  • 손실된 패킷을 자동으로 재전송하는 것

이러한 기능이 필요하다면 TCP나 다른 상위 프로토콜이 이를 제공해야 한다.

5.2 IPv4 헤더 구조

IPv4 기본 헤더의 길이는 20바이트이며, Options를 포함하면 최대 60바이트까지 확장할 수 있다.

+--------+--------+----------------+
|Version |  IHL   | DSCP/ECN       |
+--------+--------+----------------+
|           Total Length           |
+----------------------------------+
|          Identification          |
+--------+-------------------------+
| Flags  |     Fragment Offset     |
+--------+--------+----------------+
|  TTL   |Protocol| Header Checksum|
+--------+--------+----------------+
|        Source IP Address         |
+----------------------------------+
|      Destination IP Address      |
+----------------------------------+
|         Options (Optional)       |
+----------------------------------+

위 그림은 필드를 이해하기 위한 개념도이며, 실제 헤더의 정확한 비트 배치는 아래 표의 크기를 기준으로 이해하면 된다.

5.3 IPv4 필드별 설명

Version 4bit IP 버전
IHL 4bit IP 헤더 길이

Version

현재 IP 프로토콜의 버전을 나타낸다.

IPv4라면 값은 4이다.

IHL(Internet Header Length)

IPv4 헤더의 길이를 나타낸다.

IHL은 4바이트 단위로 계산한다.

예:

IHL 값헤더 길이

5 20바이트
6 24바이트
10 40바이트
15 60바이트

수신 측은 이 값을 통해 IP 헤더가 어디에서 끝나는지 알 수 있다.

그 뒤에는 TCP, UDP, ICMP 등의 데이터가 위치할 수 있다.

DSCP와 ECN

DSCP(Differentiated Services Code Point)는 트래픽에 대한 서비스 분류 정보를 제공한다.

예를 들어 음성 통신과 일반적인 파일 전송을 서로 다르게 처리하는 QoS 정책에 활용할 수 있다.

ECN(Explicit Congestion Notification)은 지원하는 장비와 프로토콜 사이에서 혼잡 상태를 표시하는 데 사용된다.

Total Length

IP 헤더와 IP 페이로드를 포함한 전체 IPv4 데이터그램의 길이이다.

예를 들어 다음 패킷이 있다고 가정하자.

IPv4 Header : 20 bytes
UDP Header  :  8 bytes
Data        : 12 bytes

이 경우:

Total Length = 40 bytes

이 값에 Ethernet 헤더 길이는 포함되지 않는다.

Identification

IPv4 단편화 과정에서 같은 원본 데이터그램에서 생성된 단편을 식별하는 데 사용된다.

Flags

IPv4 단편화를 제어하는 필드이다.

Flag의미

Reserved 예약 비트
DF Don't Fragment, 단편화 금지
MF More Fragments, 뒤에 단편이 더 있음

DF가 설정된 패킷은 경로에서 일반적인 IPv4 단편화를 수행할 수 없다.

Fragment Offset

단편이 원래 IP 데이터그램의 어느 위치에 해당하는지를 나타낸다.

8바이트 단위로 표현한다.

TTL(Time To Live)

패킷이 네트워크에서 무한히 순환하지 않도록 제한하는 필드이다.

일반적으로 IPv4 라우터는 패킷을 전달할 때 TTL을 1 감소시킨다.

출발지   TTL = 64
   ↓
Router 1 TTL = 63
   ↓
Router 2 TTL = 62
   ↓
목적지   TTL = 62

TTL이 소진되면 패킷은 폐기된다.

이때 조건이 허용된다면 라우터는 ICMP Time Exceeded 메시지를 전송할 수 있다.

Traceroute는 이러한 원리를 활용한다.

Protocol

IP 헤더 다음에 어떤 프로토콜이 위치하는지 알려준다.

값프로토콜

1 ICMP
6 TCP
17 UDP
47 GRE
50 ESP

예를 들어 Protocol 값이 6이라면 상위 프로토콜은 TCP이다.

Header Checksum

IPv4 헤더에 대한 오류 검출 값이다.

IPv4 헤더의 일부 필드는 전달 과정에서 변경될 수 있다.

대표적인 예시가 TTL이다.

일반적인 IPv4 라우터는 TTL을 감소시키면서 헤더 체크섬도 그 변경 사항에 맞춰 갱신한다.

단, 이 체크섬은 IP 페이로드 전체를 보호하지 않는다.

Source IP / Destination IP

각각 출발지와 최종 목적지의 IPv4 주소이다.

일반적인 라우팅에서는 두 주소가 유지된다.

하지만 NAT가 적용되는 경우에는 주소가 변경될 수 있다.

5.4 IPv4 단편화(Fragmentation)

네트워크 인터페이스와 링크에는 한 번에 전송할 수 있는 데이터 크기 제한이 존재한다.

이를 MTU(Maximum Transmission Unit)라고 한다.

예를 들어 Ethernet에서 흔히 사용하는 MTU는 1500바이트이다.

이보다 큰 IPv4 데이터그램을 전달해야 하는 경우에는 단편화가 필요할 수 있다.

원본 IPv4 데이터그램
         |
         v
   Fragmentation
         |
     +---+---+
     |       |
     v       v
 Fragment 1 Fragment 2

수신 측은 단편을 모아 원래 데이터그램으로 재조립한다.

단편화와 관련된 주요 필드는 Identification, Flags, Fragment Offset이다.

다만 DF가 설정되어 있으면 라우터는 해당 패킷을 단편화하지 않고 폐기할 수 있다.

단편화는 보안 분석에서 중요하다.

그 이유는 모든 단편에 완전한 TCP/UDP 헤더가 존재하는 것은 아니기 때문이다.

첫 번째 단편에 TCP 헤더가 존재하더라도 뒤쪽 단편은 해당 TCP 헤더를 포함하지 않을 수 있다.

따라서 방화벽은 IP 단편화와 재조립을 고려해야 한다.

6. IPv6 Header

6.1 IPv6란?

IPv6(Internet Protocol version 6)는 128비트 IP 주소를 사용하는 인터넷 프로토콜이다.

IPv4의 주소 공간 부족 문제를 해결하는 것이 주요 개발 배경 중 하나다.

IPv4와 달리 IPv6의 기본 헤더는 고정된 40바이트이다.

또한 IPv6는 확장 헤더(Extension Header)를 통해 여러 부가 기능을 표현할 수 있다.

6.2 IPv4와 IPv6 비교

항목IPv4IPv6

TTL 관련 필드 TTL Hop Limit
상위 프로토콜 식별 Protocol Next Header
단편화 송신 호스트와 중간 라우터에서 조건부 가능 중간 라우터는 수행하지 않음

브로드캐스트 지원 브로드캐스트 대신 멀티캐스트 등의 방식 사용

Traffic Class

IPv6 트래픽에 대한 서비스 분류와 혼잡 제어 신호에 사용된다.

Flow Label

관련된 패킷들을 하나의 흐름으로 식별하는 데 사용할 수 있다.

Payload Length

IPv6 기본 헤더 뒤에 존재하는 데이터의 길이를 나타낸다.

IPv4의 Total Length와 달리 기본 IPv6 헤더 40바이트를 포함하지 않는다.

또한 확장 헤더가 존재하면 그 길이도 포함된다. 특수한 Jumbogram 처리에는 별도의 규칙이 적용된다.

Next Header

다음에 등장하는 헤더를 나타낸다.

이는 TCP나 UDP일 수도 있고 다른 IPv6 확장 헤더일 수도 있다.

Hop Limit

IPv4의 TTL과 유사한 역할을 한다.

라우터를 통과하면서 값이 감소하고, 소진되면 더 이상 전달할 수 없다.

6.4 IPv6 Extension Header

IPv6는 필요한 경우 기본 헤더와 전송 계층 헤더 사이에 확장 헤더를 사용할 수 있다.

예시:

IPv6 기본 헤더
       ↓
Hop-by-Hop Options
       ↓
Routing Header
       ↓
Fragment Header
       ↓
TCP Header
       ↓
Application Data

모든 IPv6 패킷에 확장 헤더가 존재하는 것은 아니다.

일반적인 통신에서는 다음과 같은 구조도 가능하다.

IPv6 → TCP → Data

확장 헤더는 종류와 순서에 따라 처리 규칙이 있으며, 실제 패킷 분석에서는 Next Header 필드를 따라 해석해야 한다.

7. TCP Header

7.1 TCP란?

TCP(Transmission Control Protocol)는 신뢰성 있는 바이트 스트림을 제공하는 연결 지향 전송 프로토콜이다.

TCP가 제공하는 주요 기능은 다음과 같다.

  • 연결 설정 및 종료
  • 데이터 순서 관리
  • 수신 확인
  • 손실 데이터 재전송
  • 흐름 제어
  • 혼잡 제어

다만 TCP가 언제나 데이터 전달 성공을 보장하는 것은 아니다.

연결이 유지될 수 없거나 오류가 복구되지 않으면 통신이 실패할 수 있다.

7.2 TCP 헤더 구조

기본 TCP 헤더는 20바이트이다.

TCP Options에 따라 최대 60바이트까지 확장할 수 있다.

필드크기역할

Source Port 16bit 출발지 포트
Destination Port 16bit 목적지 포트
Sequence Number 32bit 바이트 스트림의 순서
Acknowledgment Number 32bit 다음에 수신할 것으로 기대하는 바이트 번호
Data Offset 4bit TCP 헤더 길이
Reserved 가변 예약 비트
Flags 제어 비트 연결 및 데이터 처리 제어
Window Size 16bit 수신 윈도우 광고
Checksum 16bit TCP 메시지 오류 검출
Urgent Pointer 16bit 긴급 데이터 관련 정보
Options 가변 MSS, Window Scale, SACK 등

7.3 Source Port와 Destination Port

IP 주소가 네트워크상의 컴퓨터를 식별하는 데 사용된다면 포트는 컴퓨터 안의 통신 종단을 구분하는 데 사용된다.

예:

Client
192.168.1.10:50000

Server
203.0.113.20:443

이 경우 TCP 헤더의 주요 값은 다음과 같다.

Source Port      = 50000
Destination Port = 443

일반적인 TCP 연결은 다음 네 가지 값의 조합으로 구별할 수 있다.

Source IP
Source Port
Destination IP
Destination Port

이는 흔히 TCP 4-Tuple이라고 부른다.

7.4 TCP 3-Way Handshake

TCP는 통신을 시작하기 전에 연결 설정 과정을 수행한다.

이를 3-Way Handshake라고 한다.

Client                         Server
   |                              |
   | -------- SYN -------------> |
   |                              |
   | <------ SYN + ACK --------- |
   |                              |
   | -------- ACK -------------> |
   |                              |
   |       연결 설정 완료          |

① SYN

클라이언트가 서버에 연결을 요청한다.

이때 초기 Sequence Number를 전달한다.

예:

SYN
Seq = 1000

② SYN + ACK

서버는 연결 요청을 확인하고 자신의 초기 Sequence Number를 전달한다.

SYN + ACK

Seq = 5000
Ack = 1001

SYN은 Sequence Number 공간을 1만큼 소비하기 때문에 ACK가 1001이 된다.

③ ACK

클라이언트는 서버의 SYN에 대해 최종 확인 응답을 보낸다.

ACK

Seq = 1001
Ack = 5001

이 과정을 통해 양쪽은 서로의 초기 Sequence Number를 확인하고 연결을 설정한다.

7.5 Sequence Number

TCP는 데이터를 바이트 스트림으로 다룬다.

Sequence Number는 해당 세그먼트 데이터의 첫 번째 바이트가 스트림에서 어떤 번호를 갖는지 나타낸다.

예를 들어 다음 데이터가 있다고 가정하자.

HELLO

총 5바이트이다.

이 데이터의 첫 번째 바이트 번호가 1001이라면 다음과 같이 표현할 수 있다.

H = 1001
E = 1002
L = 1003
L = 1004
O = 1005

따라서 모든 데이터가 정상적으로 수신되었다면 수신 측은 다음에 1006번 바이트를 기대한다.

7.6 Acknowledgment Number

ACK Number는 일반적으로 다음에 연속해서 받기를 기대하는 바이트 번호를 의미한다.

앞의 예시에서 HELLO를 모두 받았다면:

ACK = 1006

이라는 응답을 보낼 수 있다.

이것은 1005번까지의 바이트를 연속적으로 받았다는 의미이다.

중요한 점은 TCP의 ACK가 기본적으로 누적 확인 응답이라는 것이다.

7.7 TCP Flags

TCP Flags는 연결 설정, 종료, 재설정 등에 사용되는 제어 정보이다.

Flag의미주요 역할

SYN Synchronize 연결 시작
ACK Acknowledgment 수신 확인 정보 유효
FIN Finish 해당 방향의 전송 종료
RST Reset 연결 재설정 또는 거부
PSH Push 데이터의 신속한 전달 요청
URG Urgent 긴급 데이터 관련 정보
ECE ECN Echo 혼잡 신호 전달
CWR Congestion Window Reduced 혼잡 제어 반응 표시

자주 나타나는 조합은 다음과 같다.

Flags의미

SYN 연결 요청
SYN + ACK 연결 요청에 대한 응답
ACK 수신 확인
PSH + ACK 데이터 전달 시 자주 사용되는 조합
FIN + ACK 연결 종료 과정
RST 연결 재설정

7.8 TCP 재전송

TCP는 데이터가 손실되면 재전송을 수행할 수 있다.

예를 들어 다음 데이터를 전송한다고 가정하자.

Segment 1 : 1001~1500
Segment 2 : 1501~2000
Segment 3 : 2001~2500

Segment 2가 손실되었다고 하자.

수신 측이 Segment 3을 받더라도 1501부터의 데이터가 빠져 있다면 일반적으로 누적 ACK는 1501을 유지할 수 있다.

송신 측은 중복 ACK, 선택적 확인 응답(SACK), 재전송 타이머 등의 정보를 이용해 손실을 추정하고 필요한 데이터를 재전송할 수 있다.

이를 통해 TCP는 손실이 발생할 수 있는 IP 네트워크 위에서 신뢰성 있는 통신을 제공한다.

7.9 TCP Window Size

TCP는 수신 측이 처리할 수 있는 데이터 양을 고려해야 한다.

이를 흐름 제어(Flow Control)라고 한다.

수신 측은 TCP Window 필드를 이용해 자신이 수용할 수 있는 수신 윈도우 크기를 송신 측에 알린다.

실제 유효 윈도우 크기는 연결 협상에 따라 Window Scale 옵션의 영향을 받을 수 있다.

이 기능은 수신 측의 처리 능력을 초과해 데이터를 보내는 상황을 방지하는 데 기여한다.

흐름 제어는 수신 측 버퍼 상태에 관한 기능이고, 혼잡 제어는 네트워크 혼잡 상황을 고려하는 별도의 기능이다.

7.10 TCP 연결 종료

TCP 연결은 일반적으로 FIN과 ACK를 이용해 정상적으로 종료할 수 있다.

대표적인 종료 흐름은 다음과 같다.

Client                         Server
   |                              |
   | -------- FIN -------------> |
   |                              |
   | <------- ACK -------------- |
   |                              |
   | <------- FIN -------------- |
   |                              |
   | -------- ACK -------------> |
   |                              |

실제 종료 과정에서는 TCP 상태와 양쪽 애플리케이션의 종료 시점에 따라 FIN과 ACK가 결합되거나 다른 순서로 관찰될 수도 있다.

RST는 정상적인 FIN 종료와 달리 연결을 재설정하거나 거부할 때 사용된다.

8. UDP Header

8.1 UDP란?

UDP(User Datagram Protocol)는 비연결형 전송 프로토콜이다.

TCP와 달리 연결 설정을 위한 3-Way Handshake를 수행하지 않는다.

UDP는 데이터를 독립적인 데이터그램 단위로 전달한다.

UDP 자체는 다음 기능을 제공하지 않는다.

  • 데이터 전달 성공 보장
  • 데이터 순서 보장
  • 손실 데이터 재전송
  • TCP와 같은 흐름 제어

필요한 경우 애플리케이션이나 상위 프로토콜이 이러한 기능을 구현해야 한다.

8.2 UDP 헤더 구조

UDP 헤더는 고정된 8바이트이다.

+------------------+------------------+
|   Source Port    | Destination Port |
|      16bit       |      16bit       |
+------------------+------------------+
|      Length      |     Checksum     |
|      16bit       |      16bit       |
+------------------+------------------+
|               Data                  |
+-------------------------------------+

필드크기설명

Source Port 2B 출발지 포트
Destination Port 2B 목적지 포트
Length 2B UDP 헤더와 데이터 길이
Checksum 2B UDP 메시지 오류 검출

UDP Length는 일반적으로 UDP 헤더와 페이로드를 합친 길이를 나타낸다.

따라서 5바이트 데이터를 보낸다면:

UDP Header = 8 bytes
Data       = 5 bytes

UDP Length = 13 bytes

가 된다.

UDP 체크섬은 IP 의사 헤더(Pseudo Header)의 일부 정보도 사용해 계산한다.

IPv4에서는 UDP 체크섬을 사용하지 않는 경우가 허용되지만, IPv6에서는 일반적으로 UDP 체크섬이 필수이며 일부 특수한 예외가 존재한다.

8.3 UDP가 사용되는 이유

UDP는 TCP보다 헤더가 단순하며 연결 설정이 필요하지 않다.

예를 들어 실시간 음성 통신에서는 지연된 오래된 데이터를 무조건 다시 받는 것보다 최신 데이터를 빠르게 처리하는 것이 더 중요할 수 있다.

다만 UDP 자체가 빠른 전송이나 낮은 지연을 보장하지는 않는다.

실제 성능과 신뢰성은 네트워크 상태와 상위 프로토콜의 설계에 따라 달라진다.

대표적인 활용 사례는 다음과 같다.

  • DNS
  • 실시간 음성 및 영상 전송
  • 온라인 게임
  • QUIC 기반 HTTP/3
  • 일부 스트리밍 프로토콜

9. ICMP Header

9.1 ICMP란?

ICMP(Internet Control Message Protocol)는 IP 네트워크의 오류와 제어 정보를 전달하는 데 사용되는 프로토콜이다.

가장 잘 알려진 활용 사례는 ping이다.

하지만 ICMP는 단순히 연결 여부를 확인하는 기능만 제공하는 것이 아니다.

대표적인 기능은 다음과 같다.

  • Echo Request 및 Echo Reply
  • 목적지 도달 불가 알림
  • TTL 소진 알림
  • 일부 라우팅 관련 제어 메시지
  • 패킷 처리 오류 알림

9.2 ICMPv4 메시지 구조

ICMP 메시지는 Type에 따라 세부적인 구조가 달라진다.

일반적으로 앞부분에 다음 필드가 존재한다.

필드크기역할

Type 1B 메시지의 종류
Code 1B 세부적인 메시지 의미
Checksum 2B ICMP 메시지 오류 검출
Rest of Header 가변 메시지별 추가 정보
Data 가변 요청 데이터 또는 오류 관련 정보

대표적인 ICMP Type은 다음과 같다.

Type이름의미

0 Echo Reply Echo 요청에 대한 응답
3 Destination Unreachable 목적지 도달 불가
5 Redirect 더 적절한 경로 알림
8 Echo Request Echo 요청
11 Time Exceeded TTL 등의 제한 초과
12 Parameter Problem IP 헤더 등의 문제 알림

9.3 ICMP Echo Request / Echo Reply

일반적인 ping 과정은 다음과 같다.

PC A                          PC B
 |                             |
 | ---- Echo Request -------> |
 |                             |
 | <---- Echo Reply ---------- |
 |                             |

Echo Request는 Type 8이다.

Echo Reply는 Type 0이다.

이러한 메시지를 이용해 상대 호스트의 응답 여부와 왕복 시간을 측정할 수 있다.

다만 ping 응답이 없다고 해서 반드시 상대 호스트가 꺼져 있다는 뜻은 아니다.

방화벽 정책이나 ICMP 제한 때문에 응답하지 않을 수도 있다.

9.4 ICMP Time Exceeded

IP 패킷의 TTL이 소진되면 더 이상 패킷을 전달할 수 없다.

라우터는 해당 패킷을 폐기하고, 조건이 허용되면 출발지에 ICMP Time Exceeded 메시지를 보낼 수 있다.

Source
   |
   | TTL = 2
   v
Router 1
   |
   | TTL = 1
   v
Router 2
   |
   X TTL 소진
   |
   +---- ICMP Time Exceeded ----> Source

Traceroute는 이러한 원리를 활용하는 대표적인 진단 도구이다.

9.5 ICMP와 TCP/UDP의 차이

ICMP는 TCP와 UDP처럼 애플리케이션 데이터를 전달하기 위한 일반적인 전송 계층 프로토콜이 아니다.

ICMPv4는 IPv4 패킷의 페이로드로 직접 전달된다.

이때 IPv4 Protocol 필드 값은 1이다.

IPv4 Header
    |
    +---- ICMP Message

반면 TCP와 UDP는 다음과 같은 구조를 가진다.

IPv4 Header
    |
    +---- TCP Header
               |
               +---- Application Data
IPv4 Header
    |
    +---- UDP Header
               |
               +---- Application Data

10. 전체 통신 흐름 정리

이제 지금까지 학습한 헤더들이 실제로 어떻게 연결되는지 살펴보자.

다음과 같은 네트워크를 가정한다.

Client
192.168.1.10
     |
     |
Gateway
192.168.1.1
     |
     |
Internet
     |
     |
Web Server
203.0.113.20

클라이언트가 TCP 기반 HTTPS 웹 서버에 접속하는 상황이다.

10.1 서버 IP 주소 확인

클라이언트는 도메인 이름에 대응하는 IP 주소가 필요하다.

이미 캐시된 정보가 있다면 이를 사용할 수 있고, 그렇지 않다면 DNS 질의가 필요할 수 있다.

DNS는 UDP, TCP, 암호화된 전송 방식 등 여러 형태를 사용할 수 있다.

10.2 라우팅 테이블 확인

클라이언트는 목적지 서버의 IP 주소를 기준으로 라우팅 테이블을 조회한다.

라우팅은 패킷을 어느 인터페이스로 내보내고 어느 다음 홉으로 전달할지 결정하는 과정이다.

목적지가 다른 네트워크에 있다면 일반적으로 기본 게이트웨이를 이용한다.

10.3 ARP로 게이트웨이 MAC 확인

게이트웨이의 MAC 주소를 모른다면 ARP를 사용해 확인한다.

이때 ARP 요청과 응답이 발생할 수 있다.

10.4 Ethernet 프레임 구성

이후 클라이언트는 다음과 같은 프레임을 구성할 수 있다.

Ethernet Header

Source MAC = Client MAC
Destination MAC = Gateway MAC
EtherType = IPv4

IP Header

Source IP = 192.168.1.10
Destination IP = 203.0.113.20
Protocol = TCP

TCP Header

Source Port = 50000
Destination Port = 443
Flags = SYN

여기서 중요한 것은 Ethernet Destination MAC과 IP Destination Address가 서로 다른 목적을 가진다는 사실이다.

Ethernet Destination MAC은 현재 링크에서 패킷을 전달할 다음 장비를 가리킨다.

IP Destination Address는 최종 목적지 서버를 나타낸다.

10.5 라우터를 통한 전달

게이트웨이는 패킷의 목적지 IP를 확인한 뒤 라우팅 테이블을 이용해 다음 경로를 선택한다.

일반적인 IPv4 라우팅에서는 다음과 같은 작업이 수행된다.

  1. 수신한 프레임에서 IP 패킷을 처리한다.
  2. 목적지 IP 주소를 확인한다.
  3. 다음 경로를 선택한다.
  4. TTL을 감소시킨다.
  5. 필요한 IPv4 헤더 정보를 갱신한다.
  6. 다음 링크에서 사용할 새 데이터링크 프레임을 구성한다.

이 과정은 목적지에 도달할 때까지 여러 라우터에서 반복될 수 있다.

10.6 TCP 연결 설정

서버가 TCP SYN을 받으면 연결 요청을 처리한다.

조건이 정상적이라면 서버는 SYN+ACK를 반환할 수 있다.

클라이언트가 ACK로 응답하면 TCP 연결이 성립한다.

10.7 TLS 핸드셰이크

HTTPS를 사용하는 경우 TCP 연결 위에서 TLS 핸드셰이크가 진행된다.

이 과정에서 일반적으로 다음과 같은 작업이 수행된다.

  • 서버 인증
  • 암호화 방식 협상
  • 키 합의
  • 암호화 통신 준비

TLS는 통신 내용을 보호하는 역할을 한다.

단, HTTPS 통신에서 IP 주소나 TCP 포트와 같은 모든 헤더 정보가 암호화되는 것은 아니다.

10.8 애플리케이션 데이터 전달

연결과 TLS 설정이 완료되면 HTTP 요청과 응답을 교환할 수 있다.

데이터는 TCP, IP, 데이터링크 계층의 처리를 거쳐 상대방에게 전달된다.

수신 측에서는 반대 방향으로 헤더를 해석하고 데이터를 애플리케이션에 전달한다.

10.9 통신 종료

통신이 끝난 뒤 TCP 연결을 종료할 수 있다.

일반적인 정상 종료에서는 FIN과 ACK가 사용된다.

다만 HTTP Keep-Alive 같은 연결 재사용 메커니즘 때문에 요청 하나가 끝났다고 연결을 즉시 종료하는 것은 아니다.

11. 각 헤더는 누가 읽고, 언제 변경될까?

프로토콜을 이해할 때 가장 중요한 질문은 다음 두 가지이다.

누가 이 헤더를 읽는가?

어떤 상황에서 헤더 값이 변경되는가?

헤더주요 처리 주체변경될 수 있는 정보

Ethernet NIC, L2 스위치, 호스트 데이터링크 처리 링크마다 Source/Destination MAC 재구성
ARP IPv4 호스트 및 이웃 주소 확인 기능 요청·응답 메시지의 주소 정보
IPv4 호스트, 라우터 TTL, Checksum, NAT 주소, 단편화 필드 등
IPv6 호스트, 라우터 Hop Limit 등
TCP TCP 종단 시스템 Sequence, ACK, Flags, Window 등
UDP UDP 종단 시스템 포트, 길이, 체크섬 등
ICMP 호스트 및 라우터 오류·진단 메시지 생성과 응답

여기서 헤더가 변경된다는 것이 모든 라우터가 모든 필드를 변경한다는 뜻은 아니다.

예를 들어 일반적인 라우터는 통과하는 TCP 패킷의 Sequence Number를 임의로 변경하지 않는다.

반면 NAT 장비는 IP 주소나 포트를 변환할 수 있으며, 변경된 내용에 맞춰 체크섬도 조정해야 할 수 있다.
